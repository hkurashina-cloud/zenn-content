## はじめに

PortSwigger Web Security Academy の SQL injection ラボ、[SQL injection vulnerability allowing login bypass](https://portswigger.net/web-security/sql-injection/lab-login-bypass) を題材にします。

前回は WHERE 句のフィルタを突破して隠しデータを引き出すラボでしたが、今回は **ログインフォーム** が舞台です。ゴールは、パスワードを知らないまま `administrator` ユーザーとしてログインすること。正解 payload は `administrator'--` ですが、この記事ではいつも通り **アプリが実際に組み立てるクエリを最後まで復元** しながら、なぜこれで認証が通るのかを丁寧に追っていきます。

ログインフォームは右上の「My account」から開けます。

## ラボ概要

ユーザーがユーザー名とパスワードでログインするアプリを考えます。正規ユーザー `wiener` がパスワード `bluecheese` を送信すると、サーバ側では認証確認のために次の SQL が発行されます。

```sql
SELECT * FROM users WHERE username = 'wiener' AND password = 'bluecheese'
```

- このクエリが **1行でも返せばログイン成功**、0行なら失敗、という判定
- 認証は「ユーザー名が一致し **かつ** パスワードが一致する行が存在するか」を `AND` で確かめている

ここで重要なのは、前回と同じく **入力が文字列連結でクエリに埋め込まれる** ことです。テンプレートを図解するとこうなります。

```
SELECT * FROM users WHERE username = '   ←ここから
                                        {ユーザー名入力}
                                     ' AND password = '   ←ここまでアプリが付ける
                                        {パスワード入力}
                                     '
```

つまりユーザー名入力の直後には、アプリが必ず **閉じクォート `'` と ` AND password = '...'`** を連結します。この“見えない後半”を無効化できれば、パスワードチェックごと消せる——というのが攻撃の骨子です。

## 攻撃の狙い: パスワードチェックを丸ごとコメントアウトする

やりたいことは「`username = 'administrator'` の行を返しつつ、`AND password = ...` の条件を消す」こと。SQL の行コメント `--` を使えば、それ以降を無効化できます。

送信する値はこうです。

- **ユーザー名**: `administrator'--`
- **パスワード**: （空でよい）

## 正解の payload: `administrator'--`

ユーザー名に `administrator'--` を入れると、アプリが組み立てるクエリはこうなります。

```sql
SELECT * FROM users WHERE username = 'administrator'--' AND password = ''
```

一つずつ復元して読み解きます。

- `username = 'administrator'` … 入力の先頭 `administrator` と、それに続く `'` で **文字列がちょうど閉じる**
- `--` … ここから **行末までがコメント**
- `' AND password = ''` … アプリが付けた後半部分。**まるごとコメントアウトされて無効化**

DB が実際に評価するのは、コメントを除いた次の部分だけです。

```sql
SELECT * FROM users WHERE username = 'administrator'
```

これは `administrator` ユーザーの行をそのまま返します。**パスワードの照合は一切行われません**。アプリは「1行返ってきた＝認証成功」と判断し、`administrator` としてログインが通ります。

![administrator'-- でログインした結果、管理者としてログインできた画面](画像URLをここに)

これでラボはソルブです。

:::message
`--` の直後には多くの DB でスペースが必要ですが（`-- ` のように）、ここでは `--` の後ろにアプリ由来の `'`（＝ `--'`）が続くため、行コメントとして問題なく機能します。もし環境依存で弾かれる場合は `administrator'-- ` のように末尾スペースを明示すると確実です。
:::

## なぜ `--` の1手で認証が丸ごと吹き飛ぶのか

ログイン認証のロジックは突き詰めると「**該当行が存在するか**」の一点に集約されています。本来は `username` と `password` の2条件を `AND` で結んで安全性を担保していますが、`--` によって後半の `AND password = '...'` が消えると、条件は `username = 'administrator'` の1つだけに退化します。

- **本来**: ユーザー名が一致 **かつ** パスワードが一致する行 → 認証成功
- **注入後**: ユーザー名が一致する行 → 認証成功（パスワードは無視）

パスワードという「秘密を知っていること」を確認するはずのチェックが、クエリ構造レベルで削除されてしまう。これが認証バイパスの本質です。ユーザー名さえ分かっていれば（`administrator` は典型的に存在する）、パスワードを一切知らなくても侵入できます。

## 補足: 閉じクォートの扱いは前回のラボと表裏一体

前回の WHERE 句ラボでは、`--` を**外す**とアプリ由来の閉じクォート `'` が宙に浮いて「閉じられない文字列リテラル」になり、**500 Internal Server Error** で落ちました。今回はその裏返しで、`--` を**付ける**ことで、宙に浮くはずだった閉じクォート `'`（＝ `--'` の `'`）を **コメントの一部として飲み込ませて** 無害化しています。

どちらのラボでも鍵は同じ——**「アプリが入力の後ろに付ける `'` と後続句をどう処理するか」**。`--` は、その後続句を丸ごとコメント化することで「構文を壊さず、かつ邪魔な条件（`released = 1` やパスワード照合）を消す」という一石二鳥の役割を果たします。

## この検証から得た教訓

- **認証の強さは「条件の数」ではなく「その条件が本当に評価されるか」で決まる**。`AND password = ...` があっても、クエリ構造ごと消せるなら意味をなさない。
- **payload の後ろには、アプリが勝手に付ける“見えない後半”がある**。`' AND password = '...'` まで頭の中で復元しないと、なぜ `--` の位置がそこなのかが腑に落ちない。**閉じクォートまで含めてクエリを最後まで書き下す** のが基本動作。
- **根本対策はプリペアドステートメント（パラメータ化クエリ）**。入力を文字列連結でクエリに混ぜている限り、`--` 一発で認証ロジックは崩れる。ユーザー入力を「コード」ではなく「データ」として扱う仕組みが必須。
- 攻撃者視点では、`administrator` のような **既知・推測可能なユーザー名の存在** が前提を成立させている点も見逃せない。列挙されやすいユーザー名は、それ自体が攻撃面になる。
