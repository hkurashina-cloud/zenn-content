## はじめに

PortSwigger Web Security Academy の SQL injection 入門ラボ、[SQL injection vulnerability in WHERE clause allowing retrieval of hidden data](https://portswigger.net/web-security/sql-injection/lab-retrieve-hidden-data) を題材にします。

このラボの「正解」payload は `' OR 1=1--` です。多くの解説記事では「末尾に `--` を付けて以降をコメントアウトする」と一言で流されがちですが、この記事ではあえて **「`--` を外したらどうなるのか」** を実際に検証し、なぜ `--` が「保険」ではなく「必須」なのかを SQL 演算子の優先順位から掘り下げます。

## ラボ概要

商品一覧ページはカテゴリでフィルタできるようになっており、あるカテゴリ（例: `Gifts`）を選ぶと、サーバ側では次のような SQL が発行されます。

```sql
SELECT * FROM products WHERE category = 'Gifts' AND released = 1
```

- `category = 'Gifts'` … URL の `category` パラメータでユーザーが指定した値
- `released = 1` … **未公開（未リリース）商品を一覧から隠すための条件**。アプリ側が常に付与する

ゴールは、この `category` パラメータに SQL インジェクションを仕込み、`released = 1` の縛りを回避して **未公開商品も含めた全商品を表示させる** ことです。

## 最初の仮説: `' OR 1=1--` で全部出るはず

`category` パラメータは文字列リテラルの中にそのまま埋め込まれているので、シングルクォートで文字列を閉じてから `OR` で恒真条件をぶら下げれば、WHERE 句全体が真になって全件返るはず——という定番の発想でスタートします。

```
' OR 1=1--
```

これを埋め込むとクエリはこうなります。

```sql
SELECT * FROM products WHERE category = '' OR 1=1-- ' AND released = 1
```

これで解けるのは分かっている。でも、ここで一つ疑問が湧きました。

## 詰まりポイント: `--` を外したらどうなる？

ふと「この末尾の `--` って本当に必要なのか？ `OR 1=1` だけで押し切れないのか？」と気になりました。`1=1` はどう見ても恒真なので、コメントアウトしなくても WHERE 句全体が真になりそうな気がしたのです。

そこで、あえて `--` を外した payload を投げて挙動を確かめてみます。

### 検証: `--` なしの payload

```
' OR 1=1
```

このとき、サーバ側で組み上がるクエリは次のようになります。

```sql
SELECT * FROM products WHERE category = '' OR 1=1 AND released = 1
```

`released = 1` の条件が **コメントアウトされずにそのまま残っている** のがポイントです。パッと見「`OR 1=1` があるんだから全部真でしょ」と思いたくなりますが、ここに落とし穴があります。

### ここで効いてくる知識: SQL 演算子の優先順位

`AND` と `OR` が混在する式では、**`AND` は `OR` よりも優先順位が高い**（先に結合される）というルールがあります。四則演算で `+` より `*` が先に計算されるのと同じ構図です。

したがって、括弧なしで書かれた次の式は、

```sql
category = '' OR 1=1 AND released = 1
```

実際にはこう解釈されます。

```sql
category = '' OR (1=1 AND released = 1)
```

`1=1 AND released = 1` は `released = 1` と等価なので、式全体は

```sql
category = '' OR released = 1
```

に潰れます。つまり **`released = 1` の制約が生き残ってしまう**。結果として「カテゴリが空 or 公開済み商品」しか取れず、未公開商品は依然として弾かれたままになります。恒真条件を足したつもりが、優先順位のせいで骨抜きにされていたわけです。

### 実証結果

Burp Repeater で `--` なしの payload を実際に投げてみると、想定どおり **未公開商品は表示されませんでした**。公開済みの商品だけが返ってきて、ラボの目標は達成できません。

## 正解の payload: `' OR 1=1--`

では改めて `--` を付けた正解の形を見てみます。

```
' OR 1=1--
```

組み上がるクエリはこうです。

```sql
SELECT * FROM products WHERE category = '' OR 1=1-- ' AND released = 1
```

`--` は SQL の行コメント開始記号なので、それ以降（`-- ' AND released = 1` の部分）はまるごと無効化されます。データベースが実際に評価するのは、

```sql
SELECT * FROM products WHERE category = '' OR 1=1
```

だけ。`released = 1` の縛りが物理的に消えるため、`1=1` の恒真条件によって WHERE 句全体が真となり、**未公開商品を含む全商品が返ってきます**。

![--付きのpayloadで未公開商品を含む全商品が表示された画面](画像URLをここに)

これでラボはソルブです。

:::message
`--` の直後には半角スペースが必要なDBもあります（MySQL の `-- ` など）。PortSwigger のラボ環境では `--` に続けて空白を含む形（`-- ` の後にクォートが残る）になるため問題なく機能します。
:::

## この検証から得た教訓

- **コメントアウトは「念のため付ける保険」ではなく、`AND`/`OR` の優先順位を理解した上での「必須の一手」**。`--` を外すと、優先順位のせいで後続の `AND released = 1` が生き残り、恒真条件を足しても攻撃が成立しない。
- **`OR 1=1` だけで押し切ろうとするのは再現性が低い**。実務では `released = 1` のような後続条件が「どんな形で・いくつ」存在するか分からない。`AND (a=1 AND b=2 AND ...)` のように複数連なっていれば、優先順位頼みの攻撃はまず通らない。`--` で後続を丸ごと切り捨てるほうが、クエリ構造に依存せず確実。
- 「なんとなく動くから付けている」記号の一つひとつに、ちゃんと理由がある。**payload を丸暗記するのではなく、組み上がるクエリを頭の中で復元して評価順まで追う** 癖をつけると、未知のクエリ構造にも応用が利く。
