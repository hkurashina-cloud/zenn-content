## はじめに

PortSwigger Web Security Academy の SQL injection 入門ラボ、[SQL injection vulnerability in WHERE clause allowing retrieval of hidden data](https://portswigger.net/web-security/sql-injection/lab-retrieve-hidden-data) を題材にします。

このラボの「正解」payload は `' OR 1=1--` です。多くの解説記事では「末尾に `--` を付けて以降をコメントアウトする」と一言で流されがちですが、この記事ではあえて **「`--` を外したらどうなるのか」** を実際に検証します。結論を先に言うと、`--` を外すと未公開商品が「表示されない」のではなく、そもそも **500 Internal Server Error でクエリが落ちます**。その理由を、アプリが実際に組み立てるクエリを復元しながら追っていきます。

## ラボ概要

商品一覧ページはカテゴリでフィルタでき、あるカテゴリを選ぶとサーバ側では次のような SQL が発行されます。

```sql
SELECT * FROM products WHERE category = 'Gifts' AND released = 1
```

ここで重要なのは、アプリがクエリを **文字列連結** で組み立てているという構造です。ユーザー入力を挟んだテンプレートはこうなっています。

```
SELECT * FROM products WHERE category = '   ←ここから
                                          {ユーザー入力}
                                       ' AND released = 1   ←ここまでアプリが付ける
```

- `category = '{入力}'` … 入力をシングルクォートで囲む
- `AND released = 1` … **未公開（未リリース）商品を隠すための条件**。アプリが常に末尾へ付与する

ゴールは、この `category` パラメータに SQL インジェクションを仕込み、`released = 1` の縛りを回避して **未公開商品も含めた全商品を表示させる** ことです。

:::message
ポイントは「入力の**前**に開きクォート `'`、**後ろ**に閉じクォート `' AND released = 1` が必ず付く」こと。この“見えない後半部分”が、この記事の主役です。
:::

## 最初の仮説: `' OR 1=1--` で全部出るはず

`category` パラメータは文字列リテラルの中にそのまま埋め込まれるので、シングルクォートで文字列を閉じてから `OR` で恒真条件をぶら下げれば全件返るはず——という定番の発想でスタートします。

```
' OR 1=1--
```

これを埋め込むとクエリはこうなります。

```sql
SELECT * FROM products WHERE category = '' OR 1=1-- ' AND released = 1
```

これで解けるのは分かっている。でも、ここで一つ疑問が湧きました。

## 詰まりポイント: `--` を外したらどうなる？

ふと「この末尾の `--` って本当に必要なのか？ `OR 1=1` だけで押し切れないのか？」と気になりました。`1=1` はどう見ても恒真なので、コメントアウトしなくても WHERE 句全体が真になりそうな気がしたのです。

そこで、あえて `--` を外した payload を Burp Repeater で投げてみます。

### 検証: `--` なしの payload

```
' OR 1=1
```

結果は——**HTTP/2 500 Internal Server Error**。未公開商品が出るどころか、レスポンスが正常に返ってきません。

![--なしのpayloadを投げると500 Internal Server Errorになる](画像URLをここに)

「`1=1` は恒真なのに、なぜ 0 件でも通常表示でもなく、サーバエラーなのか？」——ここが本題です。

### なぜ 500 になるのか: クエリを最後まで復元する

多くの人（そして最初の僕）がやりがちな勘違いは、`--` なしのクエリを次のように **後半を無視して** 復元してしまうことです。

```sql
-- ❌ こう思い込みやすい（アプリが付ける後半を忘れている）
SELECT * FROM products WHERE category = '' OR 1=1
```

しかしアプリは、入力の後ろに **必ず `' AND released = 1` を連結** します。`--` がなければそれは有効なまま。実際に組み上がるのはこうです。

```sql
-- ✅ 実際のクエリ
SELECT * FROM products WHERE category = '' OR 1=1' AND released = 1
```

`1=1` の直後に注目してください。ここにある `'` は **アプリが付けた閉じクォート** です。`--` がないのでコメント化されず、DB からはこう見えます。

- `''` … 空文字列（ここは閉じている）
- `OR 1=1` … 恒真条件
- `'` … ここで **新しい文字列リテラルが開始**
- ` AND released = 1` … その文字列の中身……のはずが、**閉じるクォートが存在しない**

つまり **「閉じられていない文字列リテラル (unterminated string literal)」** が末尾に残り、SQL としてパースできず構文エラー → データベースが例外を投げ、アプリが 500 を返す、という流れです。

`released = 1` の制約が「効いてしまう」以前の問題で、**クエリが実行される前に構文で死んでいる**。これが `--` を外したときに起きる現実でした。

## 正解の payload: `' OR 1=1--` が何をしているか

改めて `--` を付けた形を見ます。

```
' OR 1=1--
```

組み上がるクエリはこうです。

```sql
SELECT * FROM products WHERE category = '' OR 1=1-- ' AND released = 1
```

`--` は SQL の行コメント開始記号なので、それ以降（`-- ' AND released = 1`）はまるごと無効化されます。DB が実際に評価するのは、

```sql
SELECT * FROM products WHERE category = '' OR 1=1
```

だけ。つまり `--` は **2つの仕事を同時に** こなしています。

1. **構文の修復**: アプリが付ける宙に浮いた閉じクォート `'` を消し、unterminated string literal を解消する（＝500 を回避する）
2. **フィルタの除去**: `AND released = 1` ごとコメントアウトし、未公開商品の縛りを消す

結果、`1=1` の恒真条件で WHERE 句全体が真になり、**未公開商品を含む全商品が返ってきます**。

![--付きのpayloadで未公開商品を含む全商品が表示された画面](画像URLをここに)

これでラボはソルブです。

## 補足: 「演算子の優先順位」はこのラボでは主役ではない

「`--` なしでも `OR 1=1` があれば、`AND` の優先順位に関係なく真になるのでは？」と考えたくなりますが、**このラボではそもそもクエリが構文エラーで実行されない** ため、優先順位の議論に到達しません。原因はあくまで「閉じクォートの不整合」です。

演算子の優先順位（`AND` は `OR` より優先）が効いてくるのは、入力が **クォートで囲まれない数値カラム** に入るような別パターンです。例えば `WHERE id = {入力} AND released = 1` に `1 OR 1=1` を入れると、

```sql
WHERE id = 1 OR 1=1 AND released = 1
→ id = 1 OR (1=1 AND released = 1)   -- AND が先に結合
→ id = 1 OR released = 1             -- released=1 が生き残る
```

となり、構文エラーにはならないものの `released = 1` の縛りが残ってしまう。**「クォート文字列コンテキスト → 500 になる」「数値コンテキスト → 優先順位で縛りが残る」** と、コンテキストによって“詰まり方”が変わるのが面白いところです。

## この検証から得た教訓

- **payload の後ろには、アプリが勝手に付ける“見えない後半”がある**。`' AND released = 1` のような後続を頭の中で復元せずに payload を組むと、「なぜか 500」の沼にはまる。**閉じクォートまで含めてクエリを最後まで書き下す** のが基本動作。
- **`--` は「念のための保険」ではなく、構文修復とフィルタ除去を兼ねる必須の一手**。特に文字列コンテキストでは、これがないとインジェクション以前に構文エラーで止まる。
- **エラーの種類は情報**。0 件でも通常表示でもなく 500 が返ったら、「フィルタで弾かれた」ではなく「クエリ構造を壊した（＝注入は届いているが文法が崩れた）」サイン。むしろ注入点として有望な手応えでもある。
- payload を丸暗記するのではなく、**組み上がるクエリを復元して構文と評価順まで追う** 癖をつけると、未知のクエリ構造にも応用が利く。
